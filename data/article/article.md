# 用 LangChain 构建可靠的 Agent：从模型循环到上下文工程

> 本文由 LangChain 官方 Python 文档整理而成。正文中的 [n] 形式都是引用标记：点击编号会打开源文件并定位到对应的字符位置；文末按编号列出被引用的 chunk，默认折叠，可以展开阅读。

## 一、三个包，三种职责

LangChain 把 Agent 浓缩成一句话：Agent = Model + Harness [1]。模型负责推理与生成，harness 负责模型循环之外的一切——提示词、工具，以及塑造模型行为的中间件。Agent 是否好用，往往取决于 harness 的工程质量，而不是模型参数。

官方把开源部分拆成框架、运行时与 harness 三层，各自解决不同的问题 [2]。LangChain 提供模型、工具和 Agent 循环的抽象与集成；LangGraph 是低层编排框架与运行时，用于构建长时间运行、有状态的应用，并允许把确定性的手工步骤和模型驱动的步骤放进同一张图 [3]；Deep Agents 则是开箱即用的 harness，自带文件系统、子 Agent 生成与长期记忆等能力 [4]。

| 层次 | 代表 | 你得到什么 |
| - | - | - |
| Harness | Deep Agents | 预置工具、提示词、子 Agent、上下文管理 |
| 框架 | LangChain | 模型与工具抽象、`create_agent` |
| 运行时 | LangGraph | 持久化、流式输出、中断、图编排 |

选择顺序也很直接：先用 Deep Agents 快速做出一件能跑的东西；需要精细定制时下沉到 `create_agent`；当流程里既有确定性分支又有自主决策时，再交给 LangGraph 编排。

## 二、Agent 的最小闭环

抛开框架，Agent 的定义非常朴素：模型在一个循环里调用工具，直到任务完成 [5]。循环之外的那层壳——提示词、工具、中间件——就是 harness [6]。理解这一点之后，很多"框架魔法"都会变得可解释：所谓配置 Agent，本质上是在设计这层壳。

一个最小的 Agent 只需要模型、工具和一句系统提示：

```python
from langchain.agents import create_agent

def get_weather(city: str) -> str:
    """Get weather for a given city."""
    return f"It's always sunny in {city}!"

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[get_weather],
    system_prompt="You are a helpful assistant",
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What's the weather in San Francisco?"}]}
)
```

代码背后仍然是"模型决定调用哪个工具、工具返回结果、模型继续推理"的循环，只是循环、消息状态和工具调度都被收进了 harness。

## 三、工具：Agent 伸向外部的手

工具决定 Agent 能做什么：获取实时数据、执行代码、查询外部数据库，以及在世界里采取行动 [7]。定义工具的成本很低——一个装饰器包住普通函数即可，函数签名里的类型提示是必需的，它直接决定工具的输入 schema；而默认情况下，函数的 docstring 会成为工具描述，用来帮助模型判断什么时候该调用它 [8][9]。

也正因如此，写工具的重点不在于代码有多复杂，而在于描述是否准确：模型只能根据名称、描述和参数结构来理解工具，含糊的 docstring 会直接变成错误调用。

## 四、上下文工程：可靠性来自"喂对信息"

Agent 出错时，第一反应通常是"模型不够强"。但官方文档的判断更克制：LLM 失败无非两个原因——模型能力不足，或者正确的上下文没有被传进去；而多数情况下，问题出在后者 [10]。于是有了上下文工程的定义：在正确的时机，把正确格式的信息和工具提供给 LLM，让它能够完成任务 [11]。

上下文按生命周期可以粗分为两类：短期记忆把对话保存在单个线程内，靠 checkpointer 持久化，线程可以随时恢复 [12]；长期记忆则跨会话保存用户偏好、历史结论等数据，通常由 LangGraph 的 store 承担 [13]。把两者混为一谈，往往会导致"聊到后面忘记前面"或者"换个会话就失忆"。

## 五、中间件、人工介入与护栏

中间件是控制 Agent 内部行为的抓手 [14]。它挂在模型调用与工具执行的前后，用来做日志、改写提示词、重试、限流，或者在必要时提前结束。

人工介入（HITL）是最典型的用法：当模型提出一个需要审阅的动作，例如写文件或执行 SQL，中间件会暂停执行并等待人的决定 [15]。这些决定被归纳为四种——原样批准（`approve`）、修改参数后执行（`edit`）、带反馈拒绝（`reject`），以及直接把人的回复当作工具结果返回（`respond`）[16]。由于暂停依赖状态持久化，HITL 必须配合 checkpointer 使用。

护栏解决的是另一类问题：在关键节点校验和过滤内容，防止 PII 泄露、提示注入或不合适的输出 [17]。它可以写成确定性的规则，也可以交给模型判断，二者常常组合使用。

## 六、结构化输出与流式响应

当 Agent 的输出要被程序消费时，自然语言就不够了。结构化输出让 Agent 直接返回 JSON、Pydantic 模型或 dataclass 这类可预测的数据结构，省去解析文本的麻烦 [18]。`create_agent` 会把校验后的结果放在状态的 `structured_response` 字段里；支持原生结构化输出的模型走 provider 策略，其余模型则回退到工具调用策略。

另一个直接影响体验的能力是流式输出：逐步显示内容，而不是等完整响应生成完再一次性返回，可以显著改善 LLM 应用的响应感 [19]。除了模型 token，流还可以承载 Agent 每一步的状态更新、思考过程和自定义进度信息。

## 七、多 Agent 与编排

多 Agent 系统用一组专业化组件协作处理复杂流程 [20]，但它并不是复杂任务的默认答案。常见的诉求其实只有三个：控制上下文规模、让不同团队独立开发、并行执行子任务。真正被广泛使用的模式是"子 Agent 即工具"：主 Agent 统一负责路由，决定何时、如何调用哪个子 Agent [21]。

再往上就是编排。LangGraph 文档把工作流与 Agent 区分得很清楚：工作流有预先确定的代码路径，按既定顺序执行 [22]；Agent 则是动态的，自己决定流程和工具用法 [23]。把两者混在同一张图里，让确定的部分可审计、灵活的部分可探索，正是 LangGraph 的核心价值。

## 八、把外部世界接进来

工具不一定要自己写。Model Context Protocol（MCP）用统一协议描述应用如何向模型提供工具和上下文，`MCPAdapter` 会连接 MCP 服务器、发现工具并转换成 LangChain 工具，直接交给 `create_agent`。适配器会根据传入的 target 推断传输方式——进程内服务器、stdio 本地脚本、远程 URL 之间的差别只在 target 上 [24]。

另一条路是检索。典型做法是把文档切块、生成 embedding、写入向量库，再把检索器接到 Agent 或 RAG 流程上：先用它检索与问题相似的段落，再交给模型 [25]。

## 九、可观测性与落地建议

Agent 的调用链比普通应用长得多，一次请求里可能包含多轮模型调用和工具执行。LangChain 的 Agent 默认支持 LangSmith 追踪，设置环境变量即可记录完整执行过程，不需要改代码 [26]。

如果要给出一条务实的落地路径，大概是：先用最小的 harness 跑通闭环，再补上记忆与工具；把高风险动作交给 HITL，把输出约束成结构化数据；当流程复杂到单 Agent 难以维护时，再引入多 Agent 与 LangGraph 编排；最后用追踪数据驱动优化。Agent 的可靠性，最终是这些工程细节的累积，而不是某一次提示词的灵光一现。
